# OpenCLScope Database 0.12.0 — Worker, Pages and UI parity audit

Reference: VulkanScope Database 1.4.12. OpenCL-only semantics retained. No synthetic reports or inferred device features.

## Mandatory publication invariants

- Worker and snapshot generator share `validateSubmission` and `DATABASE_RELEASE_VERSION` so a complete accepted producer cannot be rejected by a stale snapshot whitelist.
- Per-report POST stays atomic and canonical; duplicate report IDs are idempotent. First-time accepted reports immediately dispatch `pages.yml` when the token is configured; failed delivery is retried by the optional 15-minute published-snapshot reconciliation cron when `SNAPSHOT_PAGES_URL` points to the real Pages site.
- Pages workflow checks its actual JS bundle and tests current-producer reports. Publication requires report ID in the complete index AND the featured full-report preload, with per-report SHA-256 checks.
- Post-deployment verification retrieves the public Pages index and snapshot and requires the trigger ID. A failed check fails the release job; it is never labeled success.
- The browser loads the published cache first, checks a cheap live `/v1/sync` token, then fetches only changed index pages, rechecking when the page is visible (10-second interval). Offline and unavailable API states preserve displayed cached reports. This is near-real-time polling, not an unsupported instant-push claim.
- Full report details beyond the bounded preload remain accessible via exact read-only SHA-256 Worker endpoints. Snapshot max-size limits must be labeled and must not silently lose index entries.
- GPU logos copied from the VulkanScope reference are used only if the actual vendor string matches; unknown vendors have the generic logo. No OpenCL integrated/discrete classifications are fabricated.
- Existing OpenCLScope application 0.12.4/1204 retains the exact producer and query contract; no app version bump is necessary when changing the web Database release.

## Deployment evidence boundary

All scripts/tests can be executed offline with fixtures. Actual Cloudflare D1 storage, repository Actions dispatch, Pages deployment, new-report visibility and cron recovery require the deployer's configured credentials and published URLs. A ZIP alone does not prove these live operations succeeded.
